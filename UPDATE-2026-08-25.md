# v1.14 — correlated-theme cap (2026-08-25)

Risk control only. No strategy parameter was changed: stop 1.5, trail 1.25,
tp off, shorts off, OR 15, entry_window 60, bias 0.5 all stay exactly as they
were. Per the six-sweep standing conclusion, **no parameter change has survived
out-of-sample testing and none was made here.**

## Why

2026-08-21 and 08-24, the two most recent sessions:

| Aug 19–24 | trades | net |
|---|---|---|
| crypto-linked (BITO, IBIT, ETHA, MARA, CONL, BMNR) | 10 | **−54.80** |
| everything else (SOXS, AMLX, TSLL, MRNA) | 5 | **+30.86** |

On 08-21 the bot held MARA, CONL, ETHA, BITO and IBIT at once — five positions,
one bet, −46.92, while the day's two uncorrelated names made +22.25. On 08-24
four of five positions were crypto again.

This is the same failure class as 2026-07-23 (SMCX/SMCL/SNXX, −77.92) that
produced the v1.7 same-underlying cap. But `underlying_key` groups by the
ticker named in an ETP's title, and MARA/CONL/ETHA/BITO/IBIT are five genuinely
different underlyings while being one macro position. A sector/correlation cap
was proposed in `TUNING-ANALYSIS-2026-07-29.md` and never built. This is it.

## What it does

`selection.cap_correlated()` — greedy in score order, exactly mirroring
`cap_per_underlying`: a target is dropped when it already correlates
>= `max_correlation` with `max_per_cluster` names that survived. Runs AFTER the
same-underlying cap (so exact twins are already gone and don't consume the
theme's slot) and BEFORE the `max_targets` cut (so a dropped name frees a slot
for an uncorrelated candidate rather than shrinking the day's list).

```yaml
selection:
  max_correlation: 0.80          # 0 = off
  max_per_cluster: 1
  correlation_lookback_days: 30
```

**Measured, not a keyword list.** A theme map ("BITCOIN", "ETHER", "CRYPTO")
would catch the theme that already hurt and silently rot for the next one.
Correlation on daily returns generalises to themes nobody has named.

**Why a ratio survives the IEX feed.** Returns are IEX-over-IEX, so the
partial-tape problem largely cancels. This is explicitly NOT the v1.11 failure
mode, which was an ABSOLUTE 2M-share floor compared against ~4%-of-tape volume
and rejected 44 of 46 candidates.

## Fail-safes (the v1.11.1 lesson: unknown must never veto)

- A symbol with no return history is **kept**.
- A symbol with fewer than 10 overlapping observations is **kept**
  (`pearson` returns `None`).
- A flat/near-flat series is **kept** — guarded by a variance epsilon, not
  `<= 0`, because floating-point means leave ~1e-36 residue on a constant
  series that would otherwise yield a correlation from pure rounding noise.
  (This was a real bug, caught by the test suite during development.)
- Any failure fetching returns degrades to `{}` = cap inactive, never a veto.
- Correlations align on **date**, not list position — candidates are often
  recent listings whose histories start on different days.
- Only positive correlation counts. An inverse ETF is a different bet.

## Visibility

New log line every scan, so a silently-inert cap is detectable:

```
CORRELATION DATA: 31/40 candidates have >=10 daily returns (cap ON at corr>=0.80, max 1 per group)
CORRELATED CONL: 0.92 correlation with MARA (already taken); skipping
```

`bookkeeping.py` counts these as skip reason `correlated-theme`. If
`CORRELATION DATA` shows a low ratio, the cap is doing nothing — that is the
failure mode to watch for.

## Intraday re-screen

Names already targeted or traded today occupy their correlation group, so a
10:00 re-screen cannot quietly add a fifth crypto name to four taken at the
open. Both `build_targets` call sites in `runner.py` are wired.

## Sim fidelity

`backtest.daily_returns_from_bars()` is the sim-side twin of
`Broker.get_daily_returns()`, computed strictly BEFORE the simulated day (using
the day itself would leak the outcome into the selection that produced it).
`backtest.py` and `sweep.py` both pass it, so the backtest now selects the same
targets the live bot would. `sweep.py`'s prefetch cache is **version 2**; the
key includes the version, and the loader tolerates a v1 5-tuple by treating
returns as empty rather than crashing. Your existing 72 MB Jun–Aug cache will
be refetched once.

## Tests

`tests/test_correlation_cap.py` — 19 offline checks, no API: pearson edge cases,
date alignment, the literal 08-21 five-crypto replay (collapses to the
strongest, and the day's two winners TSLL/MRNA survive), cap=2, every
unknown-never-blocks path, both disable switches, the re-screen `taken_returns`
path, inverse correlation kept, threshold discrimination (a ~0.49 name is NOT
capped at 0.80), and strongest-of-group survives.

All 33 pre-existing tests still pass. Verified on the live machine.

## Validate before trusting it — `replay_correlation.py`

```powershell
python replay_correlation.py
python replay_correlation.py --max-corr 0.85
```

Replays the cap against 2026-07-23, 08-21 and 08-24 using the return history
the bot would have had that morning, and prints which names would have been
dropped and what the day's P&L becomes. Same validation v1.7 got.

Read it as "what the cap removes", not a precise counterfactual: it re-runs
selection only and ignores that a freed slot might have been filled by another
candidate. **Dropped winners are counted against the cap, not excused.**

### Replay result (run 2026-08-25) — VALIDATED, threshold kept at 0.80

| day | actual | with cap | dropped |
|---|---|---|---|
| 2026-07-23 | −77.92 | −56.56 (+21.36) | SMCL −21.36 (corr 0.85 w/ SMCX) |
| 2026-08-21 | −24.67 | −10.36 (+14.31) | BITO −10.56, IBIT −3.75 (0.92 w/ ETHA) |
| 2026-08-24 | −26.07 | −19.58 (+6.49) | IBIT −3.24, BITO −3.25 (0.90 w/ ETHA) |
| **total** | **−128.66** | **−86.50 (+42.16)** | |

**Zero winners dropped, 0 of 5** — the pre-committed criterion. Aug 21's two
profitable names (TSLL +13.24, MRNA +9.01) both survived.

**The +42.16 headline overstates v1.14.** 2026-07-23 predates v1.7 by one day;
SMCX/SMCL are both leveraged SMCI trackers, so the live bot ALREADY dedupes
them by name (v1.7's own replay put that day at −35.21, better than −56.56).
Counting that +21.36 double-counts a fix already in place.

**Incremental value over the caps already live: +20.80** — 08-21 (+14.31) and
08-24 (+6.49), the two days `underlying_key` could not help with because
BITO/IBIT/ETHA are genuinely different underlyings. Trial would read −21.08
instead of −41.88 had this been live.

**Threshold decision: KEEP 0.80.** A 0.85 run gives IDENTICAL results on both
days that matter, so there is no evidence for loosening — and 0.80 additionally
caught a true twin pair at 0.85 correlation, independently agreeing with what
v1.7 knows by name. Two different methods reaching the same verdict is evidence
the threshold sits in the right place.

**Two limitations.** (1) More conservative than expected: on 08-21 it kept
MARA, CONL AND ETHA, dropping only the tightest cluster — a miner equity and a
leveraged Coinbase ETF carry enough idiosyncratic variance to sit under 0.80
against spot-crypto ETFs even though narratively they are the same bet. This
REDUCES theme concentration, it does not eliminate it; catching MARA/CONL would
need ~0.65, which would start capturing unrelated names. Under-cap beats
over-cap. (2) The replay only sees trades that actually happened; live, a
dropped name frees a slot another candidate can fill and lose. Expect the real
benefit somewhat below +20.80.

## What this does NOT do

It does not create an edge. Trial expectancy is −0.54/trade and this does not
change that. It makes bad days smaller and stops the bot silently putting most
of its risk on one bet. That matters much more if this is ever funded than it
does on paper.

## If it is too aggressive

Raise `max_correlation` toward 0.90, or set `max_per_cluster: 2` to allow a
pair from each theme. 0.80 is a judgement call, not a swept value —
deliberately, since nothing in this project has survived parameter tuning.
Watch the first few sessions' `CORRELATED` lines and adjust if it is dropping
names you wanted.
