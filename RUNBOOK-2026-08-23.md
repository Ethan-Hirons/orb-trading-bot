## Track A — the five pending sweeps

Each writes `sweep_results.csv` (overwritten every run); `Tee-Object` keeps
the console table as well. Run them in order; Run 5 depends on 1–4.

> **Always use `-u` and `Tee-Object`, never a bare `>`.** A plain `>` redirect
> sends all progress into the file *and* Python block-buffers stdout when it
> isn't a terminal — so the console shows nothing and the file stays 0 bytes
> until the run ends. `-u` unbuffers; `Tee-Object` writes to console and file
> at once. (Learned the hard way on 08-23: a Run-1 sweep looked hung for
> minutes while it was working fine.)
>
> **These runs are slow.** Each sweep prefetches the full active-equity
> universe, then scores news for up to 40 candidates on each of ~44 trading
> days — roughly 1,700 API calls before the first combo simulates. Budget
> **10-30 minutes per sweep**. The returning prompt is the "done" signal.
> `--no-news` would cut most of that, but any run with a `--bias` value other
> than `off` needs the news scores, so it is not available for Runs 1, 2, 4, 5.
>
> **Run them ONE AT A TIME.** Four sweeps launched together on 08-23 left three
> empty files: they collide on Alpaca's rate limit and they all overwrite the
> same `sweep_results.csv`. Wait for the prompt before starting the next.
>
> **The prefetch is now cached** (added 08-23). The first run on a date range
> does the full universe scan and writes `.sweep_cache/prefetch_<hash>.pkl`;
> every later run with the same `--start`, `--end`, `--min-prev-volume` and
> screener settings prints `Prefetch cache HIT` and goes straight to
> simulating — seconds instead of ~15 minutes. The key covers only things that
> change the *data*; every grid dimension is applied afterwards, so Runs 1-5
> legitimately share one cache. Use `--refresh-cache` if the date range now
> includes days that were still forming when the cache was written, and
> `--no-cache` to bypass it entirely.

| relvol | n | win% | net | exp | t | maxDD | DD %eq | net/DD | tr/day |

**Monotonic on all four levels** — expectancy, win rate and drawdown improve
together as the threshold tightens. First clean monotonic signal in the whole
sequence, and in the direction the paper predicted.

**The mechanism matches the literature, not just the sign.** Avg win stays
~10.4-10.8 and avg loss ~-9.2..-9.7 at every level (payoff ratio slightly
WORSENS); the entire gain is hit rate, 49.7% -> 56.3%. The paper's relvol
filter moved hit ratio 41.4% -> 48.4% (+7.0 pts); this moves +6.6 pts. A filter
reproducing a published effect's size AND mechanism is harder to dismiss as
luck than one that merely shares its sign.

**Drawdown collapses** 202 -> 69 (9.8% -> 3.4% of equity). net/DD 1.73 is the
best figure in any of the four runs. And at 1.65 trades/day the sim finally
matches the live rate (1-2/day) — every other row simulated 4-5/day, which a
cash account with T+1 settlement cannot reach anyway.

**IMPORTANT CORRECTION to `RESEARCH-2026-08-14.md` §4.1.** That doc concluded
the IEX feed cannot support a relvol filter. True for the OPENING-WINDOW
version (5 minutes on ~4% of tape gives 857-share baselines). NOT true for this
daily proxy: prev-day volume / 20-day average is a **ratio of IEX volume to IEX
average volume**, so the venue share largely cancels — and a full session over
20 days is a vastly larger sample per observation than five minutes. The v1.11
liquidity-floor misfire was an ABSOLUTE 2M-share threshold against IEX volume;
a ratio does not have that failure mode. So a live-implementable version of the
paper's biggest lever may exist after all, off daily bars the screener already
reaches.

**Do NOT implement it yet.** n=71 at the winning threshold, t=1.41, not
significant, entirely in-sample. Shipping a live filter on in-sample post-hoc
evidence is precisely the v1.13 mistake. Run 5, then out-of-sample, then
consider.

### Why the relvol result fooled us — worth remembering

It was monotonic across 4 levels, its mechanism was hit-rate not payoff, and it
matched the paper's effect size to within half a point (+6.6 pts vs +7.0). That
was called "much harder to explain as luck." It was luck. **The four levels are
not independent tests — they are nested subsets of the same 43 days.** Selecting
the best-performing 40% of trades by ANY criterion correlated with outcome will
look monotonic and mechanistically clean. "Matches the literature" is worth far
less than "43 days, nested subsets" costs.

53 trades / +26.92.** The sim overstates trade count 3.3x and P&L by ~+96 over
two months. So the baseline row's out-of-sample +493.86 is NOT a forecast of
anything — the fidelity gap swamps the signal. Any future sim result must be
read against this ratio.

## Track B — the QQQ/TQQQ strategy (`qqq_orb.py`, new)

### What it implements

At 9:35 ET, QQQ's first 5-minute candle picks the day's direction. Bullish →
**long TQQQ**; bearish → **long SQQQ**; doji → no trade. Stop at the traded
ETF's own first-candle low. Optional 10R profit target, otherwise exit near the
close. One trade per day, one instrument.

**Why this fits your account specifically:** both directions are expressed as
*longs*, so `allow_shorts: false` costs nothing. No screener, no thin names, no
spread lottery, no relative-volume measurement — which means it sidesteps both
structural blockers from `RESEARCH-2026-08-14.md` at once (the IEX feed that
can't measure RelVol, and an account too small to hold a 20-name portfolio).
It needs 2–3 years of QQQ minute bars, not a live news feed.

Sizing risks `--risk-pct` of equity per trade, hard-capped at 100% notional
(no leverage), whole shares. Slippage is charged against you on **both** fills.
Bars are split-adjusted — SQQQ reverse-splits regularly, and raw bars would
fake 4x overnight moves.

### B1. Tuning window — 2024-01-01 → 2026-02-14

```powershell
python -u qqq_orb.py --start 2024-01-01 --end 2026-02-14 --or-minutes 5,15 --target-r off,10 | Tee-Object -FilePath qqq_tuning.txt
```

First run downloads ~2 years of minute bars for three symbols and caches them
under `.qqq_cache/` — slow once, fast forever after. If SIP returns 403, add
`--feed iex` (and treat the results as noisier — IEX is ~4% of the tape).

Then check robustness — a rule that only works at one parameter value is a
fitted artifact, not a rule:

```powershell
python -u qqq_orb.py --start 2024-01-01 --end 2026-02-14 --or-minutes 5 --target-r off --slippage-bps 0 | Tee-Object -FilePath qqq_slip0.txt; python -u qqq_orb.py --start 2024-01-01 --end 2026-02-14 --or-minutes 5 --target-r off --slippage-bps 5 | Tee-Object -FilePath qqq_slip5.txt
```

If the edge dies between 0 and 5 bps, it was never real — 5 bps on TQQQ is a
mild assumption, not a harsh one.

### B2. Holdout — 2026-02-15 → 2026-08-21. **Run this ONCE.**

```powershell
python -u qqq_orb.py --start 2026-02-15 --end 2026-08-21 --or-minutes 5 --target-r 10 | Tee-Object -FilePath qqq_holdout.txt
```

Only after B1 has picked the parameters, and only with those parameters. If you
run the holdout, tweak, and run it again, it stops being a holdout and Track B

that can't fail.

### What would make this worth paper-trading

Ex ante, written down before you look:

- Positive expectancy on the **holdout**, not just the tuning window.
- Survives 5 bps slippage.
- Max drawdown you'd actually sit through — expect 25–40%; the paper's own
  hit ratio is ~24%, so **10+ consecutive losing days is normal**, not broken.
- Not driven by one or two monster days. Check `qqq_trades.csv`: if removing
  the top 2 trades makes it negative, that's the same fragility the current
  bot has (net excluding the top 3 winners was −147.79).

### Honest limits

- The published result uses up to 4x leverage sized on QQQ across 2016–2023
  and reports ~1,484%. A long-only whole-share 3x-ETF version on ~$2k is **not
  that portfolio** and won't produce that curve.
- Leveraged ETFs decay in chop; holding is intraday-only, which limits but
  doesn't eliminate this.
- Backtest-only evidence, published 2023, no independent replication found.
- ~24% hit ratio is psychologically brutal to run manually. Know that before,
  not during.
